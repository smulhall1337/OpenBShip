SEQ reconstruction
0x402560 reads filename,start,end comma records until an asterisk terminator.
Source storage is: cursor at +0; 64 start shorts at +2; end shorts at +0x82;
handles at +0x102; twelve-byte name slots at +0x182. The modern bounded parser
accepts the observed *END* marker, ASCII resource stems <=8 characters, three
integer fields, valid frame bounds and at most 63 records. The source's full
64-record sentinel boundary is not silently assumed safe. Extra data, unsupported
instructions, path traversal, missing terminators and malformed records fail.
Original end fields are retained as SoundCue.End rather than renamed as duration.

0x4029F0 starts at most ONE queued cue each invocation. It compares that cue's
start <= current zero-based movie frame, starts it, then advances the cursor once.
Thus tied thresholds spread across successive frames: effective onset is
max(declaredStart, previousEffectiveOnset+1). This matters for MEDFIRE1/TWOFIRE2;
duplicates are not collapsed or started simultaneously by the new scheduler.

The native end-threshold loop at 0x402A98..0x402AB5 calls stop only when the stored
handle equals -1; 0x41A720 immediately ignores -1. Valid handles therefore do not
stop at their declared end thresholds in the traced path. Once the last cue has
started, cursor -1 also returns before that loop. The implementation preserves
this effective behavior: finite samples run naturally, limited by study completion.
This is source evidence, not a guessed interpretation of the third column.
Movie cleanup 0x402980 stops valid recorded handles, with an early failure/sentinel
boundary. The study always releases all its own audio at reset/end/switch/disposal,
including failure paths; it does not reproduce possible native cleanup leaks.

ClassicSequenceOracle executes only copied 0x402980..0x402ACD code with fifteen
validated absolute relocations. Sound requests/stops are recording stubs returning
successful dummy handles; file close and time calls are local return stubs. It
captures all 104 onset requests and close cleanup across the original twenty SEQs.
All onsets match the managed scheduler; no valid handle stops during frame polling.
Cleanup rows use the fixture's AFTER-FRAME-POLLS boundary, not an independently
measured original wall-clock cleanup time. These fixtures do not execute native
WAV loading, voice allocation, sound-device output or every failed-handle case.

Finite voices and modern mixing boundary
0x422320 builds SFX/<movie>/<cue>.wav and calls 0x41A990 with pool range [0,8).
It passes zero to 0x41A630, whose DirectSound path selects finite Play flags 0.
The loader scans completed same-name slots in reverse order, otherwise takes an
empty/completed slot, and fails if all eight are busy. Repeated active cues can
occupy separate slots. This is static code evidence; complete legacy sound-driver
behavior/shared pool occupancy has not been dynamically reconstructed.

ClipSound validates RIFF size, chunk lengths/padding, fmt/data presence/uniqueness,
PCM units and the observed mono/8-bit/11025 format. Ancillary chunks are bounded
but not interpreted; complete original WAV files preserve their contents. Samples
convert exactly as (byte-128)*256 to signed sixteen-bit at the SAME 11025 Hz rate.
The deterministic mixer models eight finite voices, overlapping samples, dropped
requests when full, completed-slot reuse, integer summation and signed saturation.
At nominal timing this model drops one request in TWOFIRE2. That is a model result,
not a physical original-game observation. Other legacy/global sounds could change
native pool occupancy. No managed resampling, looping or inferred cue-end truncation
is added. No claim of bit-identical DirectSound mixing, original gain/volume curves,
historical hardware latency, stereo spatialization or calibrated acoustics is made.

Audio backend and synchronization
WaveOutput owns one finite PCM buffer through x64 WinMM waveOut. WAVEHDR uses
pointer-sized fields (48 bytes on x64). Buffer memory remains owned until reset,
unprepare and close succeed; it is not freed while a driver can still reference it.
No system mixer volume or original process/registry is changed. The backend is
behind IClipOutput so a later WASAPI implementation can replace it. Existing .NET
Framework tooling plus a small finite-buffer backend avoid a new SDK/dependency
for this milestone; this is not a claim that WinMM is Microsoft's preferred new
audio API. The primary reference recommends WASAPI/Audio Graphs for new code:
[Waveform devices and data types](https://learn.microsoft.com/en-us/windows/win32/multimedia/devices-and-data-types).

While sound is active, reported device samples drive video. Samples, bytes and
millisecond position formats are checked explicitly, and backward position reports
cannot move video backward. Microsoft documents alternate return units and zero
position after open/reset:
[waveOutGetPosition](https://learn.microsoft.com/en-us/windows/win32/api/mmeapi/nf-mmeapi-waveoutgetposition).
Pause retains device position; restart resumes it. Stepping/restart/switch reset
the finite buffer, and unmute starts at the current video sample position:
[waveOutPause](https://learn.microsoft.com/en-us/windows/win32/api/mmeapi/nf-mmeapi-waveoutpause).
Reset/unprepare/close order follows ownership requirements:
[waveOutUnprepareHeader](https://learn.microsoft.com/en-us/windows/win32/api/mmeapi/nf-mmeapi-waveoutunprepareheader),
[waveOutClose](https://learn.microsoft.com/en-us/windows/win32/api/mmeapi/nf-mmeapi-waveoutclose).
No original codec or DLL is loaded. Device/open/position errors are visible and
fall back to silent visual progression; a two-second stalled-position watchdog
also prevents an audio device from holding the study indefinitely. Retrying Sound
off/on can reopen the default device. Native resource-release failures retain
owned storage rather than risking use-after-free.

Study timing remains a deliberate modern boundary: 25 fps, forty milliseconds per
frame including the last. Soundtracks end at that finite study duration. Native
movie completion is detected during the last decode and can advance the next phase
earlier than this final-frame hold. Device-clock mode may skip display frames after
a UI stall to preserve audio alignment; muted mode retains v0.7's bounded visual
catch-up. These are documented usability choices, not exact historical scheduling.
